# Arquitectura

## Componentes

### Frontend

Next.js 15 con App Router, React 18, TypeScript, Tailwind y `next-intl`. Se divide en landing pública y aplicación privada de tenant. Las llamadas privadas pasan por utilidades de autenticación Auth0 y clientes tipados en `frontend/lib/api/`.

La aplicación privada de tenant vive bajo el route group `frontend/app/[locale]/(tenant)/` (no agrega segmento a la URL) y comparte una única capa de autenticación y `TenantShell` (`frontend/components/tenant/shell/`: `TenantShell`, `TenantSidebar`, `TenantTopbar`, `TenantNavigation`, `TenantMobileDrawer`) entre todos sus dominios, en vez de un shell acoplado al CRM. La navegación agrupa por dominio de producto, no por CRM: Inicio (`/dashboard`, resumen ejecutivo del tenant), CRM (`/crm` resumen comercial, `/crm/leads`, `/crm/tasks`, `/crm/analytics` rendimiento comercial completo), Voz IA (`/voice-ai/experiences`, `/voice-ai/calls`, `/voice-ai/analytics`, `/voice-ai/telephony` con `VoiceCapacityPanel`), Automatización (`/automations/notifications`) e Integraciones (`/integrations`, transversal a toda la plataforma). Cada ruta legacy (`/crm/dashboard`, `/crm/settings/integrations(?:/.*)?`, `/crm/settings/notifications`, `/crm/settings/voice-experiences(?:/.*)?`, y el antiguo `/dashboard -> /crm`) conserva un stub `redirect()` a su ubicación nueva, preservando query params.

La UI de notificaciones se compone de `NotificationsWorkspace`, `RulesPanel`, `RecipientsPanel` y `DeliveriesPanel`. Las mutaciones se ejecutan mediante Server Actions para que el bearer token no viaje al cliente. `FieldHelp` es el componente compartido para ayudas contextuales de formularios; usa `<details>`, mantiene interacción por teclado y cierra con un clic externo.

Voice Experiences usa Server Components para resolver autenticación, permisos y datos iniciales. Sus clientes tipados son `server-only` y las mutaciones pasan por Server Actions; ningún bearer token llega a componentes cliente. El builder comparte un formulario controlado entre wizard y editor, administra schemas versionados y genera una vista previa React local que no usa micrófono, WebRTC ni endpoints de ejecución.

Agent Builder incorpora una prueba WebRTC detrás de `voice_runtime_v2`. Sus Server Actions crean la `VoiceSession` y solicitan el token sin exponer el bearer al cliente. `LiveKitVoiceRuntimeAdapter` es el único dueño del micrófono en este flujo, reproduce tracks remotos y libera Room, tracks, elementos de audio y listeners al finalizar. El adapter legacy Ultravox permanece separado para las experiencias públicas existentes.

El tema visual (`logo_url`, `primary_color`, `background_color`, `color_scheme`) vive dentro de `theme_json`, se versiona junto con el resto del contenido en cada publicación y se resuelve con la misma función (`resolveVoiceTheme`) tanto en la vista previa del editor como en el formulario público, para que ambos rendericen de forma idéntica. `color_scheme` es `light` por defecto para preservar las experiencias publicadas antes de esta funcionalidad.

Cada experiencia publicada expone además `/{locale}/voice/{slug}/embed`: la misma página pública (mismo submission, Turnstile, `context_token` y WebRTC) sin cabecera de sitio ni márgenes de página completa, pensada para incrustarse en un `<iframe>`. Un `ResizeObserver` dentro del formulario notifica su altura al documento padre vía `postMessage` (`voice-embed:resize`). El middleware de Next.js agrega `Content-Security-Policy: frame-ancestors *` únicamente a esa ruta `/embed`; el resto del sitio no declara política de framing. El SDK vanilla `frontend/public/voice-embed.v1.js` (sin build propio) monta el iframe como inline, botón flotante o modal disparado por un selector CSS del sitio anfitrión, y expone `window.VoiceEmbed` para uso imperativo desde React. El panel "Compartir / Incrustar" del listado de experiencias genera el enlace público (usando `experience.default_locale`, no el idioma del administrador) y los fragmentos de código (HTML/React/iframe) para cada modo.

### Backend

FastAPI organiza routers en `backend/app/api/endpoints/`, reglas de negocio en `backend/app/services/`, contratos en `schemas/` y persistencia SQLAlchemy en `models/`. `backend/app/main.py` ensambla middleware, CORS y routers.

El backend evoluciona de forma incremental hacia un **monolito modular**: un solo proceso, una sola base PostgreSQL/Alembic, con bounded contexts bajo `backend/app/modules/<módulo>/` (`domain/`, `application/`, `infrastructure/`, `api/`). El acceso entre módulos pasa exclusivamente por `app/modules/<módulo>/public.py`; `backend/test_module_boundaries.py` lo verifica por AST. Tool Platform (`app/modules/tools/`), Agent Builder (`app/modules/agents/`), Voice Orchestration (`app/modules/voice/`), Telephony (`app/modules/telephony/`), Scheduling (`app/modules/scheduling/`), CRM (`app/modules/crm/`), Notifications (`app/modules/notifications/`) e Integrations / Messaging (`app/modules/integrations/`) son los módulos migrados; Tool Platform es el patrón de referencia. Voice Providers (`app/modules/voice_providers/`) es un módulo hermano de Voice con frontera consolidada (registro de proveedores, adapters, credenciales). `voice_legacy`, `analytics` e `identity` exponen un `public.py` mínimo que delega en el código legacy. La frontera es de **datos**, no sólo de imports: las APIs públicas intercambian DTOs inmutables (`ToolSessionView`, `ContactRef`/`LeadRef`, `WhatsAppTemplateContract`, `BookingSummary`), nunca filas ORM ni `Any` como entidad, y las mutaciones sobre datos ajenos se piden por id al módulo propietario. Las rutas antiguas de tools (`app/services/tool_*.py`, `app/domain/tool_*.py`, `app/models/tools.py`, etc.) son shims temporales que alias el mismo módulo y ya no tienen consumidores. `app/db/mixins.py` es shared kernel (`TimestampMixin`, `_uuid`, `_utcnow`). Mapa, dependencias, ownership y roadmap: `docs/architecture/`.

### Evaluations (Module 12)

`app/modules/evaluations/` es dueño de definiciones y versiones, runs durables y resultados por criterio. Analytics conserva los hechos de llamadas; Evaluations conserva qué tan bien ocurrió la sesión; Billing mantiene la propiedad financiera. `voice_session_technical_health` es una definición system-owned e inmutable con criterios determinísticos de terminal state, runtime health y tool execution health. Usa sólo DTO de evidencia safe que Voice ya persiste; fija `agent_version_id` y evidencia hash en cada run, sin almacenar argumentos/resultados crudos ni transcripciones.

Voice consume `evaluations.public` mediante un adapter en `voice.wiring`. El run queued se escribe en la misma transacción que el estado terminal de Voice, para que ambos se confirmen o reviertan juntos. Evaluar sucede después, en `app.modules.evaluations.runtime.worker`, con batches acotados, `FOR UPDATE SKIP LOCKED`, leases y token/generation que rechazan workers obsoletos. La capa pública no carga SQLAlchemy al importarse; el acceso ORM queda en infraestructura. No se añaden endpoints ni contratos OpenAPI en este módulo.

El módulo Agent Builder (`backend/app/modules/agents/`: `domain/contracts.py` value objects, `domain/voice_selection.py` reglas de voz sin I/O, `domain/views.py` DTOs públicos, `application/service.py` (`AgentService`), `application/compiler.py` (`AgentCompilerService`), `application/queries.py`, `application/ports.py`, `infrastructure/models.py`, `api/router.py` + `api/schemas.py`, `public.py`, `wiring.py`) es dueño de `TenantAgent`/`TenantAgentVersion` como fuente de verdad provider-agnostic del agente, separada de `TenantVoiceAgentConfig` (config legacy ligada a Ultravox, propiedad de Voice Legacy). La voz del agente es `AgentVoiceConfig` (`mode: "provider"|"provider_external"`), validada localmente por `VoiceSelectionService` (sin I/O al guardar un draft) y por `validate_voice_compatibility` del registro de proveedores; `AgentService.publish()` añade un preflight remoto barato (accesibilidad de la voz o BYOK del proveedor externo, nunca genera audio). Agent Builder no conoce a Ultravox: todo lo que necesita de un proveedor pasa por `VoiceProviderPort` (vincular un agente remoto, validar su ejecución, validar una voz), enlazado en `wiring.py` a `voice_providers.public.VoiceProviderFacade`, que despacha por el registro de proveedores al adapter Ultravox y traduce sus tipos y errores a DTOs neutros (`ProviderAgentSnapshot`, `ProviderAgentImport`, `ProviderVoiceSelection`, `VoiceProviderError`). Los adapters de proveedor no importan ningún módulo en runtime. La importación de un agente Ultravox la orquesta el endpoint (`voice_providers.public.get_agent_import` → `agents.public.import_provider_agent`): el proveedor describe el agente remoto y sólo Agent Builder escribe `TenantAgent`, `TenantAgentVersion` y `runtime_binding_json` (incluido `provider_extensions`). El puente legacy de voz (`voice_agent_config_id` → `realtime.voice` + `realtime.settings.voice`) se resuelve con `voice_legacy.public.VoiceLegacyFacade`, sin relación ORM. Voice consume Agent Builder sólo vía `agents.public` (`lock_published_agent`, `get_agent_status`, `get_tool_bindings`, `compile_runtime_spec`, `describe_agent`, `agent_names`), y Agent Builder pide a Voice liberar las sesiones de un agente borrado (`release_sessions_of_deleted_agent`); `VoiceSession` ya no tiene relaciones ORM hacia las tablas de Agents. Ver `docs-local/fase-4/AGENT_BUILDER_ARCHITECTURE.md` para el diseño histórico de Fase 1/Fase 2/Sprint 0 (con nota de actualización) y `docs/PROJECT_STATUS.md` para el estado actual de la abstracción de voz.

`runtime_binding_json` también versiona parámetros de modelo y tools, ambos sobre el mismo `TenantAgentVersion` sin tablas nuevas. `realtime.settings` (p.ej. `temperature`) se valida contra `voice_registry.validate_model_settings()` (puro, contra `VoiceModel.parameters: dict[str, ParameterSpec]`, sin I/O). `tools` (top-level, sibling de `realtime`) es una lista de `{key, enabled, config}` validada contra `app.modules.tools.domain.registry` (mismo patrón que `voice_registry`: catálogo estático, `status="available"` sólo si existe un handler real en `app/modules/tools/application/dispatcher.py`). `AgentCompilerService` resuelve ambos hacia `RuntimeSessionSpecV1`: `settings` pasa tal cual dentro de `realtime`, y `tools` se recompila a `CompiledToolSpec` (`key/name/description/input_schema`, nunca `config`) como campo top-level separado — nunca dentro de `provider_overrides`, que ya bloquea `selectedTools` por diseño. El runtime (`voice-runtime/tool_dispatcher.py`) registra cada `CompiledToolSpec` como `RawFunctionTool` de `livekit-agents` en el `Agent(...)` de la sesión (sólo `serviglobal_managed`); el handler llama de vuelta a `POST /api/v1/internal/voice-runtime/sessions/{id}/tools/{key}/invoke` (mismo trust boundary `require_voice_runtime` que `/spec` y `/events`), que revalida el binding contra la versión publicada en base de datos y despacha por un allowlist literal de funciones Python (`app.modules.tools.application.dispatcher._HANDLERS`) — nunca `eval` ni import dinámico desde algo que el modelo o el runtime provean. Los handlers no conocen los servicios de otros dominios: usan los puertos `ToolPorts` (`scheduling`, `crm`, `messaging`, `sessions`, en `application/ports.py`), que `app/modules/tools/wiring.py` enlaza con `SchedulingFacade`, `CrmFacade`, `WhatsAppFacade` y `VoiceSessionFacade` (los `public.py` de cada módulo, que a su vez delegan en `BookingService`, `CrmContactService`/`CrmLeadService`, `WhatsAppMessageService` y `VoiceSessionService`).

**Custom HTTP Tools** extiende el mismo mecanismo de tools a herramientas HTTP declarativas por tenant, sin crear un segundo camino de function calling. `app.modules.tools.domain.registry` sigue siendo el catálogo estático de tools de plataforma (con handlers Python en `_HANDLERS`); `tenant_tools`/`tenant_http_tool_configs`/`tenant_tool_credentials` (`backend/app/modules/tools/infrastructure/models.py`) son el catálogo DB-backed de tools `custom.*` por tenant, reservando `calendar.*`/`whatsapp.*`/`crm.*`/`handoff.*` a plataforma (`app.modules.tools.domain.namespace`). `ToolResolverService` (`backend/app/modules/tools/application/resolver.py`) es el único punto que fusiona ambas fuentes en un `ResolvedToolDefinition` (`key/name/description/status/input_schema/source/required_integration/custom_tool_id`); `AgentService` (catálogo, validación de bindings al guardar draft, preflight de publish), `AgentCompilerService` (compilación) y `ToolDispatchService` (invocación) resuelven siempre a través de él en vez de reimplementar la rama plataforma/custom cada uno. `CompiledToolSpec` (`key/name/description/input_schema`) es idéntico para ambas fuentes — una tool custom nunca lleva `base_url`/`credencial` al runtime, así que `voice-runtime/tool_dispatcher.py` no requiere ningún cambio: sigue registrando cada tool como `RawFunctionTool` genérico. `ToolDispatchService.invoke()` bifurca al inicio por prefijo `custom.` hacia `CustomHttpToolExecutor` (`backend/app/modules/tools/infrastructure/http_executor.py`) sin tocar el camino de las tools de plataforma; el executor valida argumentos con el mismo validador que `_HANDLERS`, resuelve la credencial vía `TenantToolCredentialService` (Fernet + `INTEGRATIONS_ENCRYPTION_KEY`, igual que `TenantIntegration`; nunca decodifica salvo para el propio executor), construye path/query/body con mappings declarativos de solo lectura de claves (`app.modules.tools.domain.mapping`, sin `eval`) sobre raíces permitidas (`args`/`context`/`binding`), y llama `SafeHttpClient` (`backend/app/modules/tools/infrastructure/http_safety.py`): scheme `https` únicamente en producción, resuelve DNS y valida cada IP contra rangos privados/loopback/link-local/metadata antes de conectar, pinea la conexión a la IP ya validada preservando SNI/verificación TLS contra el hostname original (evita DNS rebinding), sin redirects automáticos, con timeout y tamaño de respuesta acotados. `TenantFeatureService` gatea todo el dominio tras `custom_http_tools_v1`, mismo patrón que `agent_builder_v2`. `POST /api/v1/tools/custom/*` (`backend/app/modules/tools/api/router.py`) es el CRUD tenant-scoped; el endpoint interno de invocación (`POST .../tools/{key}/invoke`) no cambia de contrato. Ver `docs/CUSTOM_TOOLS.md` para el detalle completo de seguridad, notación de mapping y flujo de ejecución.

**Session Context V1** provee la identidad de negocio que los handlers de tools usan en vez de confiar en argumentos de la LLM. `RuntimeSessionSpecV1.context` es `SessionContextV1` (`backend/app/modules/voice/domain/session_context.py`, mirror manual en `voice-runtime/contracts.py`): `caller`/`contact`/`lead`/`campaign` separados explícitamente (caller = identidad telefónica de la llamada; contact = persona/organización conocida; lead = un proceso comercial que pertenece a un contact) más `variables` de negocio con límites explícitos (20 keys, 60 caracteres/key, profundidad 2, ~4KB serializado) y sin secretos. `ContactResolutionService` (`backend/app/modules/voice/application/context_resolution.py`) es el único punto de resolución: `contact_id`/`lead_id` explícitos sólo si `trusted_ids=True` (nunca desde la LLM) → lookup por teléfono normalizado vía `voice_phone_service.normalize_caller_id` → sin resolver; nunca llama a `get_or_create_*` — un caller desconocido queda `contact=null`/`lead=null`, crear sigue siendo una acción explícita (p. ej. la tool `crm.create_lead`). El snapshot se persiste en `VoiceSession.session_context_json` (JSON nullable, sin tablas nuevas) al crear la sesión, y `AgentCompilerService.compile()` lo pasa tal cual a `RuntimeSessionSpecV1.context`. Hoy sólo está cableado al único punto real de creación de `VoiceSession` (`POST /api/v1/voice/sessions`, el flujo de prueba WebRTC) — inbound/outbound reales no existen conectados a Agent Builder. `ToolDispatchService.invoke()` carga este contexto y lo pasa a cada handler junto con `arguments`; los handlers que necesitan identidad (`calendar.create_booking`, `crm.create_lead`) la toman de `context.lead`/`context.contact`/`context.caller`, nunca de `arguments` — el `input_schema` visible a la LLM de esas tools ni siquiera declara `lead_id`/`contact_id`/`phone` como propiedades válidas.

`SessionContextV1` no es un objeto de estado arbitrariamente mutable: la única vía para cambiarlo después de creada la sesión es `VoiceSessionService.enrich_context()` (Fase F.1), que aplica **enriquecimiento monotónico controlado** — `unresolved → resolved` se permite, `resuelto → el mismo valor` es idempotente, `resuelto → un valor distinto` siempre falla cerrado (`SessionContextContactConflictError`/`SessionContextLeadConflictError`/`SessionContextTenantConflictError`, mensajes-código estables `session_context_contact_conflict`/`session_context_lead_conflict`/`session_context_tenant_conflict`). Existe porque `crm.create_lead` resuelve/crea un `Contact`/`Lead` a mitad de conversación y esa identidad debe quedar disponible para una tool posterior en la misma sesión (`calendar.create_booking`) sin que el LLM la provea nunca — el propio handler de `crm.create_lead` en `ToolDispatchService` es hoy el único integrador. `enrich_context()` recibe filas ORM (`CrmContact`/`CrmLead`), nunca IDs sueltos, valida `tenant_id` directamente contra ellas (los módulos externos usan `VoiceSessionFacade.enrich_context(session_id, contact=ContactRef, lead=LeadRef)`, que recarga las filas por id dentro de Voice antes de aplicar exactamente esta validación), nunca toca `caller`/`campaign`/`variables`/`source`, y reutiliza `ContactResolutionService.to_contact_context`/`to_lead_context` (públicos desde esta fase) para la misma representación segura que usa la resolución inicial. Emite `session.context.enriched` (mismo patrón sin PII que los demás eventos `session.context.*`).

**Voice Orchestration** (`backend/app/modules/voice/`) es el control plane de las sesiones de voz y nada más: `VoiceSession`/`VoiceSessionEvent` (`infrastructure/models.py`), máquina de estados (`domain/lifecycle.py`), `SessionContextV1` y `RuntimeSessionSpecV1` (`domain/`, misma forma serializada), creación y contexto (`application/session_service.py`, `application/context_resolution.py`), dispatch y cleanup LiveKit (`application/runtime_dispatcher.py`, `infrastructure/livekit_runtime.py`) e ingesta de eventos del runtime (`application/runtime_events.py`). La resolución de contexto lee contactos/leads como snapshots de `crm.public` (`CrmContextPort`) y normaliza teléfonos con `telephony.public`; nunca recibe ORM de CRM. Las proyecciones (historial `analytics.Call`, `CrmVoiceCall`, `CrmActivity`) quedan detrás de `VoiceProjectionPort` → `analytics.public`, alimentadas con `SessionProjectionFacts`; Voice no importa modelos de CRM ni Analytics. El router `voice_runtime` (`api/router.py`, mismas URLs) delega la credencial del runtime en `voice_providers.public`, la invocación de tools en `tools.public` y el dial SIP QA en `telephony.public`. SIP, rutas, capacidad y outbound siguen en Telephony (legacy, usan Voice mediante 4 shims temporales).

**Telephony** (`backend/app/modules/telephony/`) es dueño de la ruta SIP del tenant (`TenantSipRoute`: PBX, credenciales cifradas, caller id, países, `max_concurrent_calls`), del provisioning Asterisk y del trunk SIP de LiveKit, de la marcación del participante SIP, del mapeo de estados SIP, de la normalización de teléfonos y de la política de capacidad. El caso de uso "llamar a un lead" se reparte sin cambiar el orden: el adaptador CRM (`outbound_voice_call_service`) traduce HTTP y entrega un `OutboundCallLedger` (`crm.public`); `telephony.public.TelephonyFacade.place_outbound_call` ejecuta sesión → ruta bloqueada (`FOR UPDATE`) → capacidad → vínculo → dispatch (vía `voice.public.VoiceTelephonyFacade`) → espera `runtime_ready` → participante SIP → limpieza en fallo. Telephony consume Voice, CRM y Analytics sólo mediante puertos (`application/ports.py`, enlazados en `wiring.py`) y recibe la configuración del proveedor como `ProviderConfigRef`; su `domain/` es puro. El agente del PBX (`python -m app.workers.asterisk_provisioner`) sigue siendo un proceso aparte, sólo con librería estándar, ahora implementado en `infrastructure/asterisk_agent.py`. No quedan shims de Voice.

**Scheduling** (`backend/app/modules/scheduling/`) es dueño del tiempo y las reservas: disponibilidad, horarios, recursos, equipos, Round Robin, excepciones, tipos de cita, configuración de agenda por agente, el ciclo de vida del booking (`BookingService`) y sus tablas — incluidas `crm_bookings`/`crm_booking_events`, que el nombre físico asigna a CRM pero gobierna Scheduling. Google Calendar y Cal.com son adapters internos (`infrastructure/google|calcom`), no bounded contexts. CRM aporta el cliente de la reserva y recibe la actividad de timeline por puertos (`BookingCustomerPort`, `CrmActivityPort`) enlazados a `crm.public` en `wiring.py`; Notifications recibe un *hecho* (`booking.created|cancelled|rescheduled`) a través de `BookingEventPublisherPort` y de la infraestructura de eventos de dominio existente, sin que Scheduling la importe (única excepción temporal: el adaptador en `wiring.py`). El comando de reserva es propio (`CreateBookingCommand`), los endpoints de CRM, Tools, Agent Builder y Voice Legacy llaman a `scheduling.public` y los routers del módulo (`/api/v1/scheduling`, integraciones Cal.com/Google/recursos y el webhook de Cal.com) conservan sus URLs sin navegar ORM. La asignación Round Robin se serializa con locks de fila en PostgreSQL sólo durante la decisión (milisegundos): la disponibilidad, incluido Google FreeBusy, se evalúa antes y sin locks.

Consistencia de reservas (Scheduling): (1) la misma clave de idempotencia *confiable* de create (`tenant_id + booking.create + key`) devuelve siempre el mismo booking lógico y no vuelve a llamar al proveedor; (2) un mismo recurso no puede tener dos bookings activos (`pending|accepted|scheduled|confirmed`) con intervalos `[start, end)` solapados; (3) cancelaciones repetidas provocan como máximo una llamada de cancelación al proveedor; (4) reprogramaciones repetidas al mismo destino provocan como máximo una llamada de reprogramación. **No hay exactly-once frente a Google/Cal.com**: si una llamada al proveedor expira sin respuesta, la operación queda `provider_unknown`, el booking local `pending` sigue bloqueando el slot y nada se repite automáticamente (reconciliación posterior, fuera de este sprint). Para reservas Cal.com sin recurso local el proveedor sigue siendo la fuente de verdad y la protección de slot es best-effort. Mecánica: `tenant_booking_operations` (unique `tenant_id, operation_type, idempotency_key`; estados `pending → provider_pending → completed|failed|provider_unknown`; el INSERT con la constraint es el árbitro final de las carreras y el perdedor recarga/espera sin lock de BD) y `crm_bookings.scheduling_resource_id` (FK + índice `tenant, resource, start, end`; `metadata_json["scheduling_resource_id"]` queda como espejo legacy). Flujo: operación → lock de fila del recurso (corto, sin I/O) → re-chequeo de solapes → booking local `pending` → COMMIT → proveedor → finalización. **Orden de locks**: operación → recurso → booking. Ningún lock de BD cubre una llamada a Google/Cal.com. Una *exclusion constraint* GiST (`btree_gist`) podría reforzar el lock de fila más adelante. La clave de create no la fija el LLM (la deriva Tool Platform de `session_id` + el `invocation_id` del voice-runtime); en HTTP es el header opcional `Idempotency-Key`. Cancel/reschedule usan claves naturales (booking; booking + estado actual + destino), sin cambio de contrato. Identidad de la llamada de herramienta: el voice-runtime toma `FunctionCall.call_id` de LiveKit (inyectado por tipo como `RunContext`, nunca parte del `input_schema` visible al LLM; si no cabe en `[A-Za-z0-9._-]{1,64}` se normaliza con un digest determinista `lk-<sha256>`; sin `call_id` falla cerrado) y lo envía como `invocation_id` → Tools lo convierte en `voice:{session_id}:{call_id}` → idempotencia de operaciones de booking en Scheduling. Un intento HTTP nuevo de la misma llamada lógica produce la misma clave; llamadas distintas, claves distintas. `invoke_tool` sigue siendo un único intento HTTP (sin retry automático) y las custom tools no heredan esta garantía. Cancelación en Google: el error de `delete_event` ya no se absorbe; se propaga con su cadena causal y, si es de transporte (timeout/conexión), la operación queda `provider_unknown` sin marcar el booking como cancelado localmente, sin publicar `booking.cancelled`, sin actividad de timeline y sin reintento ciego. **Deuda conocida (fuera del PR #121)**: (A) *Scheduling Provider Outcome Classification*: hoy `is_outcome_unknown` clasifica por tipo/nombre de excepción (timeouts, conexión) en lógica de dominio; algunos HTTP 5xx recibidos tras enviar la petición siguen tratándose como fallo definitivo aunque su resultado sea desconocido. Objetivo: que los adapters clasifiquen (`ProviderDefinitiveFailure` para 400/401/403/404/409 conocidos vs `ProviderOutcomeUnknown` para timeouts, resets y ciertos 5xx, según el contrato de Google/Cal.com) en lugar de crecer listas de strings. (B) *Provider Unknown Reconciliation*: las operaciones `provider_unknown` quedan congeladas a propósito (booking `pending`/tentativo, slot bloqueado, sin reintento). Un reconciler futuro consultará el estado remoto (create: `provider_booking_id/uid`, metadata y correlación; cancel: evento inexistente/cancelado; reschedule: fecha remota = destino o = origen) y completará la operación, permitirá un reintento seguro o la dejará incierta. Sin cron/worker/endpoint en este cambio. (C) *Reschedule en `provider_unknown`*: el intervalo remoto anterior y el intervalo local tentativo (el nuevo destino, que sigue bloqueando el slot) pueden divergir hasta la reconciliación; no se revierte ni se reintenta automáticamente. (D) *E2E real con Google Calendar y Cal.com en staging* (OAuth, sincronización, disponibilidad, reservar con Meet, cancelar, reprogramar; Cal.com: `/v2/me`, sincronización, reserva, cancelar, reprogramar; y desde Agent Builder `calendar.check_availability`/`calendar.create_booking`): hoy sólo hay fakes. **Garantías que aún no existen**: no hay exactly-once frente a Google/Cal.com, la clasificación de 5xx es incompleta y no hay reconciliación.

**CRM** (`backend/app/modules/crm/`) es dueño de contactos, leads, pipeline, timeline de actividades, tareas, contextos de llamada y llamadas de voz CRM: `crm_contacts`, `crm_leads`, `crm_pipeline_stages`, `crm_activities`, `crm_tasks`, `crm_call_contexts`, `crm_voice_calls` y `crm_voice_call_events` (ORM en `infrastructure/models.py`, sin relaciones ORM hacia Analytics ni Identity: las FKs `owner_agent_id`, `created_from_call_id`, `last_call_id`, `call_id` y `assigned_to_user_id` se conservan como ids). `domain/` es puro (reglas de pipeline, normalización de teléfono, DTOs inmutables), `application/` contiene los casos de uso y sus puertos (`TaskAssigneePort` → `identity.public`, `SchedulingPort` → `scheduling.public`, `AnalyticsPort` → `analytics.public`, `LeadHistoryPort` y `CallPayloadPort`, adaptadores legacy temporales) enlazados únicamente en `wiring.py`, y `api/` expone las rutas puramente CRM (pipeline, leads, etapas, notas, actividades, tareas, métricas, borrado) con las mismas URLs, RBAC, payloads y OpenAPI. El resto de módulos accede sólo por `crm.public`: `CrmFacade` (perfiles `LeadProfile`/`ContactProfile`, snapshots por id con la semántica histórica no tenant-scoped, `record_activity`/`stage_activity`/`upsert_call_activity`, contextos de llamada, `process_call_event`, query del dashboard) y `CrmVoiceCalls`, el *ledger* de llamadas de voz cuyas escrituras corren en la transacción del llamador y **nunca hacen commit**. `crm_whatsapp_messages` **no** es de CRM: pertenece a Integrations / Messaging (`app/models/crm.py` ya no existe). El dashboard agregado (`CrmDashboardMetricsService`) es un read-model de composición CRM + Analytics + capacidad telefónica: su parte CRM es una query pública y la composición permanece fuera; `CallSummaryService` compone CRM + Analytics + Integrations y consume CRM por `crm.public`; Voice Legacy consume CRM sólo vía `crm.public` (el parseo de payloads de proveedor vive en el adaptador `legacy_call_payload_adapter`). Sin cambios de esquema, de migraciones Alembic (una sola head), ni de contratos HTTP/OpenAPI (257 rutas idénticas). **Deuda conocida del módulo CRM**: (a) el borrado de artefactos de Forms al eliminar leads pasa por `crm.wiring.LegacyLeadHistory` (excepción temporal allowlisted; Messaging y Email ya se desreferencian por `integrations.public`); (b) el adaptador de payloads Ultravox (`legacy_call_payload_adapter`) y `ultravox_ingestion_service` siguen siendo Voice Legacy: CRM sólo recibe un `CallRef` y un payload opaco; (c) la ingesta (`CrmIngestionService`) conserva nombres de evento de llamada (`call.started|joined|ended|billed`) hasta retirar la ruta Ultravox directa; (d) la componente conexa de imports que incluye CRM creció (6 → 42 módulos) porque `crm.wiring` enlaza puertos hacia Analytics, Identity y Scheduling, mientras la proyección de Analytics usa `crm.public`: se reduce al migrar Analytics. Corrección de concurrencia (probada primero sobre PostgreSQL real, 4/4 fallos): `get_or_create_contact` (teléfono y email), la creación de las etapas por defecto, la concurrencia de leads abiertos entre los flujos de servicio y de llamada conectada (respetando la regla deliberada del ciclo form-first) (primitiva única `claim_or_create_open_lead` con lock de la fila del contacto, usada por todos los caminos de creación) y la deduplicación de actividades por transición de etapa/ingesta ya no exponen `IntegrityError` bajo concurrencia.

Voice Runtime separa Control Plane y Data Plane. El backend fija la versión publicada, crea una Room determinista y despacha el job; `voice-runtime/` obtiene el spec por HTTP/JWT interno y ejecuta `AgentSession` con Ultravox, sin DB. El navegador recibe un token corto tenant-scoped para esa misma Room con grants de micrófono exclusivamente. El estado `connected` requiere el primer transcript final; agent ready, participante, entrada y salida de audio se registran como eventos detallados.

El outbound SIP de Sprint 7 usa el mismo Control Plane y Data Plane: LiveKit sigue siendo transporte/sesión y Ultravox el motor conversacional. El flujo crea primero `VoiceSession(channel="sip", direction="outbound")`, enlaza una única `CrmVoiceCall`, despacha el agente a la Room determinista y espera el evento persistido `voice.agent.ready`; sólo después `LiveKitSipService.create_sip_participant(..., wait_until_answered=true)` conecta el número por el `livekit_outbound_trunk_id` persistente de la ruta tenant. Nunca se crea un trunk por llamada. La persistencia correlaciona `voice_session_id`, `crm_voice_call_id`, Room, trunk, identidad del participante y `sip_call_id`; el número no se escribe en eventos ni logs. Ambos flags (`voice_runtime_v2` y `livekit_sip_outbound_v2`) son necesarios, por lo que deshabilitar cualquiera restaura la ruta legacy sin cambiar contratos existentes.

`analytics.application.projection_service.VoiceCallProjectionService` (módulo 11, alcanzado por `analytics.public.VoiceCallProjectionFacade`) consume `VoiceSession` y sus eventos para todos los canales reales del runtime. Una llamada CRM operativa o evidencia de participante/conversación activa un `analytics.Call` único con `external_call_id=voice-session:{session_id}`; `external_provider` es el proveedor de IA, mientras `channel`, `direction` y `runtime_engine` permanecen conceptos separados. `CrmVoiceCall` sólo se actualiza si ya está enlazada; `CrmActivity` sólo se crea para contacto/lead validado del mismo tenant, por lo que una prueba WebRTC sin CRM aparece en Historial global pero nunca en Conversaciones de un lead. El runtime guarda mensajes comprometidos de usuario y asistente como `voice.transcript.final` en `VoiceSessionEvent`; la actividad CRM expone una proyección ordenada de esos eventos cuando hay contexto. El backfill manual ejecuta el mismo servicio sin inferir cierres ausentes.

El PBX permanece como infraestructura SIP genérica. Los endpoints generados heredan de `serviglobal-tenant`; `ultravox-tenant` es sólo un alias de compatibilidad. Así, Asterisk no conoce el proveedor de IA: LiveKit origina SIP hacia el host/puerto y las credenciales cifradas de la ruta, mientras el runtime une al agente Ultravox en la misma Room. Estados SIP estructurados se proyectan a `busy`, `rejected`, `no_answer` o `failed`; cualquier fallo terminal intenta cerrar la Room para no dejar una sesión huérfana.

Las credenciales de proveedor de voz son tenant-scoped, no un `ULTRAVOX_API_KEY` global del contenedor `voice-runtime`. `voice-runtime` nunca almacena ni configura credenciales de proveedor: cada job las resuelve en tiempo de ejecución llamando a `GET /api/v1/internal/voice-runtime/sessions/{session_id}/credentials/{provider}` a través de `ControlPlaneCredentialResolver` (`voice-runtime/src/serviglobal_voice_runtime/credentials.py`), ligado al `session_id` del job — nunca a un `tenant_id` que el runtime pudiera enviar directamente. El Control Plane resuelve la `VoiceSession`, deriva su tenant, valida que el provider coincida con el de la sesión, y reutiliza `VoiceConfigService.get_active_provider_config`/`decrypt_api_key` sobre `TenantVoiceProviderConfig` (la misma fuente de verdad que usa la UI de Integraciones) para devolver la clave descifrada. La clave vive sólo en memoria durante el job; nunca aparece en `RuntimeSessionSpecV1`, metadata/tokens de LiveKit, eventos o logs. El contrato (`ProviderCredentialResolver`/`ProviderCredential` en `credentials.py`) es provider-agnostic: agregar ElevenLabs, OpenAI u otro proveedor no requiere cambiar la forma de la credencial ni el endpoint, sólo un adapter nuevo detrás del mismo `RealtimeProviderFactory`.

El rollback legacy obedece la misma frontera y resuelve la clave desde `TenantVoiceProviderConfig`; no existe fallback a `ULTRAVOX_API_KEY`. En `provider_managed`, el binding versionado guarda sólo el ID remoto y la revisión observada. Antes de cada ejecución, `UltravoxAgentCallFactory` vuelve a consultar el agente con la clave de la `VoiceSession`, clasifica tools, registra drift sin mutar la versión y crea una sola call con overrides allowlisted.

Notifications vive en `backend/app/modules/notifications/`: dominio, casos de uso, ORM/router y runtime estan separados. `public.py` expone DTOs inmutables y entradas para Scheduling, Voice e Integrations. Scheduling publica hechos de reserva por su wiring; Voice publica eventos de llamada; Messaging reporta estados por la API publica. `python -m app.workers.notification_worker` conserva el CLI del worker y procesa claims con lease, recuperacion y reintentos; la validacion de concurrencia requiere PostgreSQL.

**Integrations / Messaging** (`backend/app/modules/integrations/`, módulo 8) es dueño del catálogo de integraciones y su auditoría (`tenant_integrations`, `tenant_integration_events`), de WhatsApp (config, plantillas, Flows, ledger `crm_whatsapp_messages`, envíos y webhook de Meta), de Email (config Resend, plantillas, renderer, assets, envíos) y de Chatwoot (config, inbox, webhook, Platform API): 13 tablas con ORM en `infrastructure/models.py`, sin navegación ORM hacia otros módulos. No es dueño de Scheduling, Voice, Forms, CRM, Notifications, Identity, Storage ni Billing: los consume por `*.public`/puertos enlazados en `wiring.py`. `domain/` es puro; `application/` depende de `ports.py` (proveedores Meta/Resend/Chatwoot, secretos, features, Storage, Forms, schema de contexto de Voice, Notifications) y mapea los errores de proveedor a `ProviderError`; los adapters viven en `infrastructure/`. `integrations.public` es import-light y expone DTOs `frozen`: `IntegrationsFacade`, `IntegrationEvents` (única vía para escribir/leer la auditoría, con metadata sanitizada), `WhatsAppFacade`, `EmailFacade` y `ChatwootFacade`. Las URLs, RBAC y payloads no cambian (OpenAPI de 257 rutas y DDL de 79 tablas idénticos); `/api/v1/integrations/voice/*` conserva el prefijo pero pertenece a Voice. El webhook de Meta valida la firma, parsea el payload en el adapter y procesa eventos neutrales: los estados nunca retroceden (`read` no vuelve a `delivered`), un inbound reintentado no se duplica y el estado final se informa a Notifications por `notifications.public`. Un resultado de Meta sin `provider_message_id` queda `manual_review` y no se reintenta. Forms y la config legacy de Voice siguen en `app/models/integrations.py` (residuo, sin alias). La validación de concurrencia usa `test_integrations_postgres.py` sobre la base `serviai_integrations_test`.

**Analytics** (`backend/app/modules/analytics/`, módulo 11) posee `agents` (proyección de reporting/proveedor, no la identidad canónica `tenant_agents` del Agent Builder), `calls`, `call_events` y `metric_snapshots_daily`: hechos de llamadas, ledger de eventos con `dedup_key`, dashboards (`/api/v1/dashboard/*` salvo uso/ahorro de Billing), proyección de sesiones de voz y limpieza por tenant. Voice, CRM y Agents entran por puertos enlazados sólo en `wiring.py`; los demás módulos consumen `analytics.public` (sin ORM). Las escrituras concurrentes de llamadas, agentes y eventos convergen por los uniques existentes.

**Billing** (`backend/app/modules/billing/, módulo 10) posee `tenant_billing_plans`, `tenant_usage_alerts` y `external_provider_pricing`. La aplicación separa interpretación de uso, planes, alertas, pricing y admisión de llamadas; `UsageMeterPort` recibe hechos de `analytics.public.AnalyticsUsageFacts`, que conserva los filtros y el final inclusivo del período. Identity consume la fachada de onboarding y Billing consulta/cambia tenants mediante `identity.public`; el estado de uso del plan y `Tenant.status` siguen siendo estados distintos. Analytics conserva `calls`, `call_events`, `metric_snapshots_daily`, `agents` y el dashboard analítico; su migración como módulo 11 reemplazará el adapter por `analytics.public`.

### Datos

PostgreSQL es la base principal. Alembic administra el esquema. Los dominios persistentes son identidad/tenant, llamadas/analítica, CRM, billing/uso, integraciones y notificaciones. Notificaciones usa `tenant_capabilities`, `tenant_notification_rules`, `tenant_notification_recipients`, `domain_events` y `notification_deliveries`. Los binarios de email se almacenan mediante `StorageService` en disco local o S3 compatible; la DB guarda metadata. Chatwoot es multi-tenant vía `tenant_chatwoot_configs` (una Account por tenant, `mode` external/managed, token cifrado, `webhook_key` único) y `tenant_chatwoot_inboxes` (inboxes adicionales opcionales); no hay tabla ni configuración global de credenciales por tenant. La excepción es `CHATWOOT_PLATFORM_API_TOKEN`: un token de Super Admin de la instancia compartida, global y fuera de `tenant_chatwoot_configs`, usado sólo por `ChatwootPlatformClient` para aprovisionar Accounts nuevas en modo managed (crea un usuario `administrator` dedicado por Account, no un Agent Bot — sus tokens no tienen permiso sobre la API de cuenta).

## Voice Provider Abstraction V1

El contrato versionado `AgentVoiceConfig` tiene dos rutas: `mode="provider"` selecciona una voz del catálogo Ultravox y llega a `RealtimeModel(voice=<id>)`; `mode="provider_external"` admite sólo ElevenLabs a través de Ultravox y llega a `RealtimeModel(external_voice={"elevenLabs": ...})`. El runtime no envía `voice` y `external_voice` juntos. Para ElevenLabs son obligatorios `voice_id` y `settings.model` (string libre no vacío, máximo 80 caracteres); `speed`, `stability`, `similarity_boost` y `use_speaker_boost` son opcionales.

El draft se valida localmente, sin I/O. El preview genera audio sólo por acción explícita y puede consumir cuota. Publish realiza un preflight remoto sin generar audio: consulta metadata de la voz de catálogo o confirma BYOK ElevenLabs mediante un `prefix` no vacío en la cuenta Ultravox del tenant. El runtime repite la validación defensiva antes de construir opciones LiveKit. ServiGlobal conserva únicamente la clave Ultravox tenant-scoped; no gestiona una clave ElevenLabs directa.

## Límites de confianza

- Auth0 autentica la aplicación privada; el backend resuelve usuario, membresía, rol y tenant.
- Las rutas tenant derivan `tenant_id` del contexto autenticado.
- Las rutas `/api/v1/admin/...` requieren autorización de plataforma y pueden seleccionar tenant explícitamente.
- La familia `/api/v1/admin/notifications` es una excepción nominal: también admite roles tenant. Toda operación sobre recursos deriva el tenant de `AuthContext`; el catálogo común sigue autenticado y ningún endpoint acepta `tenant_id` del body o query.
- Webhooks verifican firma o secreto cuando el proveedor lo soporta. Chatwoot no firma sus webhooks salientes: el aislamiento por tenant usa un `webhook_key` opaco en la URL (`POST /api/v1/webhooks/chatwoot/{webhook_key}`) más un cross-check de `payload.account.id` contra la Account configurada.
- Herramientas internas de voz usan secreto compartido y nunca aceptan un tenant arbitrario sin resolver contexto seguro.
- Los secretos por tenant se cifran; las respuestas sólo indican presencia mediante campos como `has_secret`.

## Flujos principales

### Prueba WebRTC de agente

1. Un administrador tenant crea una `VoiceSession` `webrtc`; el backend deriva tenant y fija la versión publicada.
2. LiveKit crea el dispatch en `sg-vs-{session_id}` y el runtime obtiene `RuntimeSessionSpecV1`.
3. El navegador obtiene un token room-scoped, entra a esa misma Room y publica un único micrófono.
4. El runtime ignora al participant agente, registra al humano y `AgentSession` entrega su audio a Ultravox.
5. El primer transcript final marca la sesión `connected`; la respuesta vuelve como track LiveKit y el browser la reproduce.
6. Al colgar, participante, adapter, `AgentSession` y modelo liberan recursos y la sesión termina. Sin participante, el runtime aplica timeout configurable.

### Llamada a CRM

1. La landing o el CRM solicita/inicia una llamada.
2. Cada ruta tenant usa el mismo identificador `route-<uuid>` como usuario SIP y nombre de endpoint PJSIP; el backend lo deriva y la UI no permite sustituirlo.
3. Ultravox ejecuta la llamada y envía eventos.
4. El backend normaliza y persiste la llamada de forma idempotente; el worker consulta el estado del proveedor como respaldo cuando falta el evento terminal.
5. Los servicios CRM resuelven contacto/lead, contexto y etapa.
6. `VoiceCapacityService` centraliza los estados que ocupan un canal SIP, registra saturaciones y cierres de respaldo en `tenant_integration_events`, y calcula la capacidad actual aislada por tenant.
7. El dashboard separa el rendimiento reportado por Ultravox de la capacidad SIP actual; sus contadores de capacidad respetan el período, mientras ocupación y cupos son una fotografía en vivo.
8. El dashboard y timeline consultan la información ya persistida.

### Email

1. El usuario compone o previsualiza contenido seguro.
2. Backend valida lead, email, template, tokens y assets dentro del tenant.
3. Resend recibe el mensaje con idempotency key.
4. Se actualiza `TenantEmailSend` y se registran actividad y evento de integración.

### Reserva

1. CRM o herramienta de voz consulta slots con configuración tenant.
2. `BookingService` crea primero la reserva CRM en estado pendiente.
3. `CalComClient` opera con Cal.com y devuelve identificadores seguros.
4. CRM, timeline y eventos se actualizan; el webhook reconcilia cambios posteriores.

### WhatsApp y voz

Cada canal conserva configuración, cliente, servicio de negocio, persistencia, endpoints y pruebas propios. Comparten identidad tenant, timeline CRM y eventos de integración, sin compartir secretos ni payloads completos.

`TenantWhatsAppTemplate` modela un ciclo de vida propio (`draft → pending → approved | rejected`, más `disabled`) separado del estado crudo de Meta (`meta_status`). Una plantilla llega a `status="approved"` por dos caminos: sincronización masiva de plantillas ya aprobadas en Meta Business Manager (`source="meta_sync"`, variables `POSITIONAL` `{{1}}`), o creación local (`source="tenant_authored"`, variables `NAMED` `{{nombre}}`) seguida de envío a Meta (`WhatsAppConfigService.submit_template`) y sincronización manual de estado (`sync_template_status`). `WhatsAppTemplateService.get_synced_template()` es el único punto de verdad para "¿esta plantilla se puede enviar?": exige `status=="approved"`, sin importar el origen.

Flow Studio V1 permanece dentro de la misma integración y reutiliza `TenantWhatsAppConfig`, el token cifrado y el WABA ID. `TenantWhatsAppFlow` guarda una fila por versión; `published` y `deprecated` son inmutables. El frontend edita únicamente `builder_json` versión 1. `WhatsAppFlowCompiler` lo valida y produce Flow JSON 7.3 canonicalizado con hash SHA-256; `WhatsAppFlowService` aplica ownership tenant, snapshots de Context Schema, versionado, persistencia y eventos; `WhatsAppCloudClient` concentra create, metadata, multipart asset upload, status, publish, deprecate y delete. El navegador nunca llama a Graph API.

La generación desde Context Schema incluye `ask_if_missing` y `prefill_and_confirm`, preserva el binding en el builder y excluye `trust_prefill`, `internal_only` y `collect_during_call` porque V1 es estático. El snapshot evita que cambios futuros del schema alteren una versión existente. No existe todavía ingestión de respuestas, Data Exchange, endpoint encryption ni runtime de voz desde WhatsApp.

### Automatizaciones y notificaciones

1. Un cambio de reserva o llamada entra a `NotificationEventPipeline`, que crea o reutiliza un `DomainEvent` con identidad idempotente y payload seguro.
2. `NotificationOrchestrator` selecciona capacidades y reglas activas, evalúa condiciones, resuelve destinatarios y calcula `scheduled_for`.
3. Se crea o reconcilia una `NotificationDelivery` mediante una clave idempotente por evento, regla, canal y destinatario.
4. El worker reclama lotes vencidos con lease. `WhatsAppNotificationExecutor` vuelve a comprobar cancelaciones, ownership del claim y vigencia del evento antes de enviar.
5. El resultado actualiza entrega y mensaje CRM. Los errores transitorios siguen la política de reintentos; entregas antiguas o inconsistentes pasan por recuperación, `manual_review` o estado terminal.
6. La UI tenant consulta resumen, reglas, destinatarios y entregas con destinos enmascarados; nunca recibe claim tokens, payloads internos ni secretos.
7. `notification_event_schemas.py` es la fuente única de metadata para UI, validación administrativa y runtime: relaciona capacidad/evento con versión, campos tipados, operadores, formatos, rutas de destinatario y un ejemplo sintético seguro.

El evaluador admite composición `all`/`any` y rutas seguras sobre diccionarios; no usa `eval`. El endpoint de dry-run reutiliza el validador, evaluador, mapper y resolver de destinatarios de producción, pero no publica eventos, no crea entregas y no invoca WhatsApp. Las mutaciones y pruebas de reglas generan auditoría técnica sin payloads, variables, previews ni destinatarios.

### Invariantes de la UI de notificaciones

- Una regla WhatsApp ejecutable necesita una plantilla con `status="approved"` (importada por sync desde Meta o creada en la app, enviada y aprobada), además de todos sus parámetros obligatorios mapeados.
- Campos y operadores se seleccionan desde el contrato del evento. Números, booleanos, enums y fechas usan controles tipados; los operadores de existencia no conservan un valor residual.
- Cambiar la capacidad limpia el evento dependiente. Las reglas antiguas con rutas fuera del contrato quedan visibles como configuración obsoleta y no se guardan hasta corregirlas.
- Las variables de plantilla se generan desde los parámetros Meta y las rutas del evento; el preview y la prueba muestran sólo datos sintéticos o introducidos por el administrador y destinatarios enmascarados.
- Los diálogos largos usan encabezado fijo en su fila, cuerpo con `overflow-y-auto` y `DialogFooter` en una fila separada.
- Cada campo del formulario de reglas conserva una ayuda contextual traducida. El contenido se abre desde el ícono y se oculta con cualquier clic externo.
- Destinos y destinatarios se muestran enmascarados. Los cambios no deben introducir `tenant_id` en payloads del frontend.

### QA de Agent Builder

`VoiceSession.purpose` separa `production` de `qa` sin sobrecargar `channel`; `qa_context_mode` es una dimensión de request independiente del transporte y conserva `preloaded` como default compatible. El modo `conversation` rechaza contexto CRM suministrado por el cliente. WebRTC inicia sin caller; SIP deriva el caller exclusivamente de `to_phone`, que es identidad confiable del transporte, y mantiene Contact/Lead/variables vacíos hasta un enriquecimiento monotónico real. WebRTC QA reutiliza `VoiceRuntimeDispatcher`, token LiveKit y el adaptador web. SIP QA y `OutboundVoiceCallService` reutilizan `VoiceSessionSipService` para ruta tenant, dispatch, espera de `voice.agent.ready` y participante SIP; sólo el flujo productivo crea `CrmVoiceCall`. La consola lee `VoiceSessionEvent` mediante un DTO allowlisted y nunca recibe argumentos o resultados completos de tools.

## Principios de cambio

- CRM es la fuente de verdad comercial.
- La integración externa no debe saltarse servicios de dominio.
- Mantener cambios mínimos en routers/modelos compartidos.
- Registrar metadata segura, no payloads completos.
- Preservar idempotencia y aislamiento tenant en reintentos y webhooks.


## Identity / Tenancy (Sprint 9)

`app.modules.identity` owns authentication context, tenant and membership lifecycle, roles, feature grants, bootstrap, onboarding orchestration, and access auditing. Its ORM is isolated in `identity.infrastructure.models`; consumers use immutable views and the lazy `identity.public` facade. Auth0 and temporary Billing / Analytics adapters are composed in `identity.wiring`. No schema migration is part of this move. PostgreSQL concurrency acceptance is still required before marking the sprint complete.

Billing boundary hardening (Sprint 10): `tenant_billing_plans.tenant_id` and `tenant_usage_alerts.tenant_id` retain foreign keys to `tenants.id` without ORM relationships to Identity's `Tenant`. Billing's `alerts` / `billing_plan` relationship remains internal.

### Voice Experiences y binding canónico (PR #134)
`app/modules/voice_experiences/` conserva el ownership de Experience y ExperienceVersion. Cada Experience queda ligada a `TenantAgent` mediante `agent_id`; cada versión publicada conserva `agent_id` y fija `agent_version_id` exacto al publicar, mientras `agent_config_id` continúa como referencia legacy. La resolución pasa por `agents.public`; las tablas canónicas pertenecen a Agent Builder y no existe navegación ORM entre módulos. Este cambio no crea VoiceSession ni altera el runtime público.

### Public WebRTC canónico (PR #135)
El WebRTC público de Voice Experiences usa el runtime canónico: `context_token` → `ExperienceVersion` exacta (`agent_id` + `agent_version_id`) → `VoiceSession` (Voice) → room LiveKit → participante browser y `voice-runtime` (RuntimeSessionSpecV1 → proveedor). El browser sólo recibe `server_url` + `participant_token` (efímero, sólo micrófono); no conoce proveedores ni IDs internos. `TenantVoiceRuntimeCall` queda como *public launch ledger* (claim one-shot, idempotencia/recovery, correlación CRM y `voice_session_id`); su estado `ready` no es lifecycle: eso es `VoiceSession.status`/eventos. Voice Experiences consume Voice sólo por `voice.public` (`create_session_from_agent_version`, `attach_crm_call`, `ensure_webrtc_join`); la generación del participant token vive en Voice y la comparte el endpoint QA autenticado. Sin fallback silencioso a Ultravox: con `VOICE_RUNTIME_V2` apagado o Agent no `active` el launch falla cerrado. `tenant_voice_runtime_calls.launch_runtime` (`legacy_provider` | `canonical_voice_session`, NOT NULL + CHECK) es el discriminador explícito del rollout: las filas existentes se migran como `legacy_provider` y una fila legacy nunca se promueve a `VoiceSession` (un launch legacy en vuelo puede tener ya una llamada de proveedor, sea cual sea su `status`); los webhooks de proveedor no mutan filas canónicas. `SessionContextV1` sigue siendo el contrato de contexto del runtime: Voice Experiences construye las variables sólo con campos pre-llamada (`ask_if_missing`, `prefill_and_confirm`, `trust_prefill`), sin `locale` (metadata de sesión, no variable) y las valida contra `SessionContextV1` (vía `voice.public.validate_session_variables`) ANTES de consumir el token. Voice valida la configuración LiveKit antes de despachar: sin configuración la sesión queda `requested` y el mismo token se recupera después. Callback/PSTN sigue en el runtime legacy hasta PR #136 y `legacy_runtime` se limpia en PR #137.
